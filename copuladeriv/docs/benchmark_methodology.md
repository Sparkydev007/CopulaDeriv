# CopulaDeriv — Benchmark Methodology Documentation

This document specifies the benchmark methodology for the CopulaDeriv project. It ensures that performance results are reproducible, comparable, and clearly distinguished from other metrics.

## 1. Hardware environment

All benchmarks should document the following hardware specifications:

| Component | Specification (to be recorded per test run) |
|-----------|--------------------------------------------|
| CPU | Model, manufacturer, core count, clock speed |
| Memory | Total RAM, type (DDR4, DDR5, etc.) |
| Storage | Disk type (SSD, HDD), interface (NVMe, SATA) |
| GPU | (If applicable; not used in current CPU-only benchmarks) |

**Important**: Benchmarks must record the exact CPU model and clock speed. Different hardware will produce different runtimes, making comparisons invalid without this documentation.

## 5. Random seed policy

### Reproducibility requirement

All benchmarks must use a **documented random seed** so that results are reproducible. The seed must be reported in the benchmark output.

### Seed usage

- **Default seed**: 42 (used consistently across all Python tests and the C++ demo)
- **Seed reporting**: The seed used must be included in the benchmark CSV/output header
- **Different seeds**: Running the same benchmark with different seeds should produce different runtime results (due to different random draw durations) but comparable statistical results (price estimates, SEs)

### Python seed implementation

```python
import numpy as np
rng = np.random.default_rng(seed)  # seed = 42 (or documented value)
```

### C++ seed implementation

The C++ `RandomGenerator` class uses `std::mt19937_64 engine_(seed)` with seed defaulting to 42.

## 6. Warm-up procedure

### Purpose

A warm-up period allows the CPU to enter its optimal performance state and for any just-in-time compilation or caching effects to stabilize.

### Recommended procedure

1. **Run a short warm-up benchmark** (e.g., N = 1,000 paths) before the actual timing run
2. **Discard the warm-up runtime** from the final results
3. **Run the timed benchmark** with the full N (e.g., N = 1,000,000 paths)

**Rationale**: Modern CPUs may have frequency scaling (Intel SpeedStep, AMD Cool'n'Goove) that takes a few milliseconds to stabilize. Also, NumPy/SciPy may have initial compilation/cache effects.

### Documentation requirement

The warm-up policy must be documented in the benchmark results, e.g.:
```
Warm-up: 1,000 paths, discarded from timing results.
Timed run: 1,000,000 paths, median of 5 repetitions.
```

## 7. Repetition count

### Statistical reliability

Each benchmark configuration must be repeated multiple times to measure runtime variability and compute the median runtime.

### Recommended repetition count

- **Minimum**: 3 repetitions per configuration
- **Recommended**: 5 repetitions (balance between reliability and time)
- **Maximum**: 10+ repetitions for publication-quality results

### Computing the median

After collecting N runtime measurements $t_1, t_2, \dots, t_k$:

$$\text{median\_runtime} = \text{median}(t_1, t_2, \dots, t_k)$$

The median is preferred over the mean because it is robust to outliers (e.g., one unusually long run due to OS interruption).

### Example output

```
Repetitions: 5
Runtimes (seconds): [0.421, 0.398, 0.415, 0.403, 0.428]
Median runtime: 0.415 s
```

## 8. Median runtime

### Definition

The median runtime is the middle value of the repetition runtimes, providing a robust measure of typical execution time.

### Calculation

Given $k$ runtime measurements (where k is odd, typically 3-5):

1. Sort the measurements: $t_{(1)} \leq t_{(2)} \leq \dots \leq t_{(k)}$
2. The median is $t_{((k+1)/2)}$, the $((k+1)/2)$-th order statistic

For k = 5: median = 3rd smallest of 5 measurements.

### Reporting

The median runtime should be reported with units (seconds) and the number of repetitions used.

**Example**:
```
Median runtime: 0.415 s (5 repetitions)
```

## 9. Runtime variability

### Interquartile range (IQR)

The IQR describes the spread of the runtime measurements:

$$\text{IQR} = Q_3 - Q_1$$

where $Q_1$ is the 25th percentile and $Q_3$ is the 75th percentile of the repetitions.

### Coefficient of variation (CV)

The CV normalizes the standard deviation by the mean:

$$\text{CV} = \frac{\text{std}(t_1, \dots, t_k)}{\text{mean}(t_1, \dots, t_k)} \times 100\%$$

### Reporting

Both the median and a variability measure should be reported:

```
Median runtime: 0.415 s (5 repetitions)
IQR: 0.012 s (0.035 s to 0.047 s)
CV: 2.9%
```

## 10. Throughput calculation

### Monte Carlo throughput

**Definition**: The number of simulated paths processed per second.

$$\text{Throughput} = \frac{N}{\text{median\_runtime}}$$

where:
- $N$ is the number of simulation paths
- $\text{median\_runtime}$ is the median runtime in seconds for those $N$ paths

**Example**: If N = 1,000,000 paths and median runtime = 0.415 s, then:

$$\text{Throughput} = \frac{1{,}000{,}000}{0.415} \approx 2{,}410{,}000 \text{ paths/second}$$

### Reporting requirement

Throughput must always be reported alongside the median runtime and N:

| Metric | Value |
|--------|-------|
| Number of paths (N) | 1,000,000 |
| Median runtime | 0.415 s |
| Throughput | 2.41M paths/second |

### HFT latency disclaimer

**Do not claim that Monte Carlo throughput measures HFT order-processing latency**. These are fundamentally different metrics:

- **Monte Carlo throughput**: Millions of simulated paths per second. This is a batch-processing metric for option pricing analytics.
- **HFT event latency**: Microseconds per individual market event (order arrival, trade execution). This is a real-time, low-latency networking/metrics.

The project explicitly states: "Monte Carlo throughput is not equivalent to HFT event latency." Any presentation or resume entry must respect this distinction.

### Example throughput table

| Implementation | N | Median runtime | Throughput | Hardware | OS | Compiler |
|----------------|-----|----------------|------------|----------|----|----------|
| Python | 1,000,000 | 2.13 s | 470K paths/s | Intel i7-9700K | Windows 10 | Python 3.13.5 |
| C++20 | 1,000,000 | 0.38 s | 2.63M paths/s | Intel i7-9700K | Windows 10 | g++ 13.2.0, -O3 |

## 11. Memory measurement

### Measurement approach

Memory usage should be measured where practical, but the primary focus is on runtime throughput and price accuracy.

### Python memory

- NumPy arrays of size N × 2 (for copula samples) × 8 bytes per float64
- Additional arrays for Z, S1_T, S2_T, payoffs, etc.
- Estimated memory: roughly $N \times 2 \times 8 \times \text{factor} \approx 16N$ bytes (factor accounts for temporary arrays)
- For N = 1,000,000: ~16 MB (well within typical RAM capacities)

### C++20 memory

- Similar array-based approach; fixed allocations; no Python interpreter overhead
- May be slightly more memory-efficient due to absence of Python object overhead

### Reporting (optional but recommended)

```
Memory usage: ~16 MB for N = 1,000,000 paths (Python)
Memory usage: ~8 MB for N = 1,000,000 paths (C++20, estimated)
```

**Note**: Exact memory measurement requires profiling tools (e.g., Python's `tracemalloc`, C++'s Valgrind/heap-check). This is optional for v1.0; the focus is on runtime and correctness.

## 12. Statistical uncertainty

### Monte Carlo error vs. model risk

- **Monte Carlo error** (sampling uncertainty): Reduced by increasing N. Quantified by the standard error SE = exp(-rT) * s / sqrt(N).
- **Model risk**: Error due to model specification (copula type, GBM assumption, risk-neutral parameters). Does NOT decrease with larger N.

**Important distinction**: When reporting benchmark results, clearly separate the Monte Carlo standard error from any model-risk assessment.

### Standard error reporting

Each benchmark result must include:

| Metric | Value |
|--------|-------|
| Price estimate | e.g., 12.345 |
| Standard error | e.g., 0.012 |
| 95% CI | e.g., (12.321, 12.369) |

### Example statistical report

```
Price estimate: 12.345
Standard error: 0.012
95% confidence interval: (12.321, 12.369)
Monte Carlo paths: 1,000,000
Repetitions: 5
Median runtime: 0.415 s
Throughput: 2.41M paths/second
```

### CLT applicability

The normal approximation for the CI assumes the CLT applies. For N ≥ 10,000 and smooth payoff functions, the approximation is typically accurate. For smaller N or skewed payoffs, report the CI with appropriate caveats.

## 13. Fair comparison methodology

### Comparing Python vs. C++20

When comparing Python and C++20 implementations, the following conditions must be met for a fair comparison:

| Condition | Requirement |
|-----------|-------------|
| **Same random seed** | Both implementations must use the same seed for reproducibility comparison |
| **Same number of paths (N)** | N must be identical |
| **Same hardware** | Both run on the same machine (or explicitly document different hardware) |
| **Same compiler/library versions** | C++ compiler flags and Python library versions must be documented |
| **Same benchmark code logic** | The core pricing loop should implement the same mathematical formula |
| **Same optimization level** | C++ compiled with `-O3`; Python without artificial slowdown |

### Invalid comparison practices (avoid)

- Comparing a single Python run with a single C++ run on different hardware without documentation
- Claiming HFT-grade latency from Monte Carlo throughput
- Comparing different N values without normalizing paths/second
- Omitting the standard error or CI from the comparison

### Reasonable comparison output format

```
Comparison: Python vs C++20 best-of call (rho=0.0, N=1,000,000)

Python:
  Median runtime: 2.13 s
  Throughput: 470K paths/s
  Price: 12.345 ± 0.012
  Seed: 42

C++20:
  Median runtime: 0.38 s
  Throughput: 2.63M paths/s
  Price: 12.344 ± 0.012
  Seed: 42

Interpretation: C++20 is approximately 5.5x faster throughput for these parameters.
Note: Same seed used; price estimates agree within Monte Carlo error.
```

## 14. Benchmark script template

### Python benchmark script skeleton

```python
#!/usr/bin/env python3
"""Benchmark script for CopulaDeriv."""

import time
import numpy as np
from copuladeriv import pricing

# === Configuration ===
N = 1_000_000      # Number of paths
rho = 0.0          # Correlation
seed = 42          # Random seed
S1_0, S2_0 = 100.0, 100.0
r, q1, q2 = 0.04, 0.01, 0.015
sigma1, sigma2 = 0.20, 0.25
T = 1.0
K = 100.0

# === Record environment ===
print(f"Python: {__import__('numpy').__version__}")
print(f"Seed: {seed}")
print(f"Paths: {N}")
print()

# === Warm-up ===
print("Warm-up run (discarded)...")
_ = pricing.monte_carlo_best_of_call_price(
    S1_0, S2_0, r, q1, q2, sigma1, sigma2, T, K, N, rho=rho, seed=seed
)

# === Benchmark repetitions ===
repetitions = 5
runtimes = []

for i in range(repetitions):
    start = time.perf_counter()
    result = pricing.monte_carlo_best_of_call_price(
        S1_0, S2_0, r, q1, q2, sigma1, sigma2, T, K, N, rho=rho, seed=seed + i
    )
    end = time.perf_counter()
    runtimes.append(end - start)

median_runtime = np.median(runtimes)
throughput = N / median_runtime

# === Output ===
print(f"Median runtime: {median_runtime:.3f} s")
print(f"Throughput: {throughput:,.0f} paths/s")
print(f"Price: {result['price']:.4f}")
print(f"SE: {result['standard_error']:.4f}")
print(f"95% CI: {result['confidence_interval']}")
```

### C++20 benchmark skeleton

```bash
#!/bin/bash
# Benchmark the C++20 copuladeriv executable

N=1000000
rho=0.0
seed=42

# Warm-up (discard output)
./copuladeriv --paths $N --rho $rho --seed $seed > /dev/null

# Time repetitions
for i in $(seq 1 5); do
    start=$(date +%s%N)
    ./copuladeriv --paths $N --rho $rho --seed $((seed + i))
    end=$(date +%s%N)
    echo "Run $i: $((end - start)) ns"
done
```

## 15. Checklist for a valid benchmark run

Before recording a benchmark result, verify:

- [ ] Hardware specifications documented (CPU, RAM, OS)
- [ ] Compiler and optimization flags documented
- [ ] Python version and library versions recorded
- [ ] Random seed used and reported
- [ ] Warm-up procedure completed and discarded
- [ ] At least 3 repetitions ran; median computed
- [ ] Runtime variability (IQR or CV) reported
- [ ] N (number of paths) reported
- [ ] Median runtime reported in seconds
- [ ] Throughput = N / median_runtime reported with units
- [ ] Price estimate, SE, and 95% CI computed and reported
- [ ] For Python/C++ comparisons: same seed, same N, same hardware documented
- [ ] HFT latency NOT claimed or implied
- [ ] All files referenced in the benchmark results exist and are reproducible
